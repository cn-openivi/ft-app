# OpenIVI FT: source-code comparison of open GPS dead-reckoning implementations
Date: 2026-11-03. Scope: user scenarios tunnel / 10–100 m multipath / Moscow-style GNSS jamming and spoofing. Source-only assessment; **NOT** an architecture-change authorization, source transplant, new APK, or live-car acceptance.

## Concrete findings, NOT README-only estimates

| Codebase | What is directly reusable | Why it is not a drop-in replacement |
|---|---|---|
| **TinyEKF** | Small EKF arithmetic, GNSS innovation/covariance, lightweight Android Kotlin adaptation already in FT | Has no timestamp alignment, GNSS spike continuity, wheel source validation, source arbitration or navigation-output API |
| **OFFGRID** | Bounded 40-tick delay history in Fusion.kt; zero-motion speed correction; heading-gyro bias refinement; optional route-constrained matching; vehicle-speed model uncertainty interface | Model primarily infers speed from phone/bicycle IMU, while FT has wheel-derived vehicle speed. Heading setup requires a quiet calibration period. **Critical spoofing weakness**: Fusion.kt `updateGnss` auto-translates filter position to rejected GNSS after `N_REJECT = 5` inconsistent fixes in GENERAL mode; continuous fake coordinates could drag trajectory to spoof point. DO NOT copy this recovery policy |
| **Naviator** | Kotlin source examples of zero-velocity updates and nonholonomic vehicle constraint, map-match adapter, diagnostic recorder, measurement update Joseph covariance | 6-state EKF lacks bias states; phone mounting affects axes, GNSS outage tests chiefly synthetic masking of real-recorded GPS. Own Sep 18 FINAL_AUDIT_SUMMARY admits earlier heading-ground-truth leakage and sharply worse corrected drift; ML not robust. `final_validation_status.md` also documents old Android model-contract discrepancy, so verify state before claiming ready-to-integrate |
| **robot_localization** | Mature sensor-frame contracts, covariance, timestamps, reprocessing of delayed measurements, GNSS/odometry fusion strategies | ROS 2/TF/Eigen stack unnecessary for Android FT; cannot just include package into Gradle |
| **FusionCore** | Strongest proven regression approach for *these three threats*: GNSS physics displacement gate after blackout, sustained-spike rejection without accidental coast-induced gate relaxation, adaptive 5-sample GNSS continuity (10–12m spikes), independent GNSS recovery testing, delayed-measurement history/replay, bias and odometry-scale diagnostics | 23-state UKF + C++ Eigen and ROS build are much heavier. **"Standalone" CMake is not currently ROS-free as-is**: `fusioncore_core/CMakeLists.txt` still does `find_package(ament_cmake REQUIRED)` and `find_package(eigen3_cmake_module REQUIRED)`; `CMakeLists_standalone.txt` includes that directory. Requires nontrivial CMake cleanup and NDK/JNI/ABI integration. Not a ready Android AAR |

## CRITICAL pitfalls found in source, beyond advertised features
1. OFFGRID GENERAL-mode automatic re-anchor after five rejected fixes is unsafe as a sole GNSS spoof countermeasure. We must never infer validity merely from a cluster of self-consistent GPS fixes.
2. FusionCore's 5-sample continuity solves a problem our current TinyEKF NIS alone does not: a 10m one-off receiver jump can be *inside* EKF innovation covariance. The project has tests `test_continuity_auto.cpp` including 12m spike and clean GNSS reacquisition after blackout.
3. FusionCore documents a **bad implementation** of continuity history spanning a 461-second outage, which then incorrectly rejected the returning real GNSS. Therefore, continuity observation history must be invalidated/reinitialized on actual GNSS gaps **without losing our last trusted vehicle-motion prediction**. Separate continuity and odometric trust.
4. FusionCore `test_gnss_coast.cpp` checks an 8s sustained +60m fake GNSS stream remains rejected; coast covariance inflation must NOT make persistent spoof pass later. Our existing TinyEKF grows uncertainty during long outages; pure NIS may eventually accept a far bogus fix. Use a separate physically plausible displacement check that is independent of EKF uncertainty (as an input acceptance rule, **not** a second navigation estimator).
5. FusionCore exposes re-anchor hooks but default `gnss_reanchor_enabled=false`; copying OFFGRID's unconditional re-anchor is NOT justified.
6. Naviator corrected benchmark shows that IMU-only accuracy and route claims can be severely overstated by GNSS heading leakage. FT should replay **full blackout** withholding position, course, velocity reference and all selected GNSS-derived aids, using only calibrated OEM wheel/gyro IMU.
7. ZUPT from Naviator is useful mainly as a **wheel-speed-zero pseudo-measurement**, not proof that a phone's accelerometer/gyro indicates car stop. NHC is not a direct patch into current 4-state TinyEKF (which lacks velocity cross-track states); that would require explicit architecture approval.
8. OFFGRID's road-map matcher assumes available offline road graph and can hide wrong-turn decisions when multiple parallel roadways/ramps exist. It cannot guarantee Yandex Auto guidance without AA LOCATION subscription or a supported navigation-output path.

## Recommended decision: DO NOT REPLACE TinyEKF at this stage
Keep the small pinned MIT TinyEKF translation already in FT for a single source-neutral 2D estimator. The lowest-risk, fewest-new-dependencies solution is to **implement selectively inside the existing DR service**, modeled on source-proven FusionCore behavior:
- P0: pass a pinned timeline of selected CAR/PHONE GNSS, wheel speed, yaw and longitudinal acceleration into the *same* EKF. Never switch absolute GNSS origin automatically.
- P0: build simple, bounded GNSS continuity + dynamics acceptance **in the same TinyEKF measurement ingestion path**; 5-fix short-term trend when available; incorporate speed/turn evidence, not just covariance. Keep adaptive calibration from good non-spoof candidates only. Do not make an automatic GPS recentering rule after N rejects.
- P0: preserve GNSS observation timestamps and bounded delayed-arrival replay; test 50–1000ms delayed fixes with synchronized motion. Existing raw ICCOA timestamps and units unverified: do not infer.
- P0: correct GNSS reacquisition after long blackout via independent wheel/gyro physical plausibility and stable heading; no forced fix after N rejects; do not set new arbitrary 120s/150m DR timeout.
- P0: regression tests for (a) tunnel including turn, (b) 10m, 30m, 100m multipath and sustained 60m spike, (c) fake airport coordinates at good claimed accuracy after 5, 50, 500 rejected fixes, (d) genuine return after long gap, (e) heading leakage-free replay. Tests should run source-only and never claim live HU field evidence.
- P1: zero-velocity observation when OEM wheel speed is VERIFIED 0 and vehicle motion consistent, to bound gyro bias; optional road map matching only if an approved offline map source and clear confidence are available.
- P0 OUTPUT BLOCKER: a private FT DR coordinate does not automatically navigate mirrored Yandex or Android Auto. Confirm Android Auto subscribed LOCATION sensor and precise fused/synthetic labeling before wiring. No OS mock-location bypass.
