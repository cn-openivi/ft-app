# Правила публикации описаний FT (с FT170)

Обязательно для **каждого** GitHub Release в `cn-openivi/ft-app`, включая prerelease, пересборку или второй тег с тем же номером FT.

Каноническое решение Nexus: `FT-RELEASE-NOTES-RU-GATE-20261113.v1` (2026-11-13).

## Что увидит пользователь

Заголовок: **FT183 — конкретное назначение изменений**, без SHA или названий веток.

1. **Что нового** — только реально добавленные возможности данной сборки.
2. **Что исправлено** — реальные исправления, понятные без чтения исходников.
3. **Что проверить на машине** — при необходимости: ещё не подтверждённое поведение.
4. **Статус** — тестовая или принятая сборка; явно указать, проводилась ли проверка на реальном ГУ.

Отличия описываются **от предыдущего опубликованного релиза**, а не от произвольного коммита. Если номер FT повторяется с другим тегом, указывать только дополнительные отличия и что унаследовано, не выдавая старые функции за новые. Если новых функций нет, честно написать «Новых функций в этой сборке нет», но должно быть хотя бы одно конкретное изменение в исправлениях. Аналогично для отсутствия исправлений.

Нельзя переносить неподтверждённые функции из планов, представлять CI, сборку или наличие кода как доказательство успешной работы на ГУ, автоматически публиковать `generate-notes` вместо пользовательского описания.

## Технические данные

**В публичном заголовке и описании запрещены** SHA, SHA-256, подписи сертификата, идентификаторы CI, хеши коммитов, номера job/run, списки изменённых файлов и технические паспорта. Они остаются во внутренних `PROVENANCE`, `SHA256SUMS`, манифестах сборки, Drive и Nexus — не удалять и не ослаблять проверки подписи/сборки.

## Обязательный шаг ДО публикации

1. Составить отдельный `*.md` для конкретного тега по фактическому сравнению с предыдущим релизом. Шаблон: `docs/releases/TEMPLATE.ru.md`.
2. Запустить локальный gate:
   ```bash
   python3 tools/release_notes/validate.py --tag "xa60-ft183-XXXXXXXX" --file "docs/releases/FT183-ИЗМЕНЕНИЯ.md"
   ```
3. Публикующий workflow **обязан** использовать содержимое проверенного файла как `body`, а не генерировать служебное описание. Если gate не пройден или файл отсутствует, **публикация запрещена**; уже собранный APK и доказательства сохранить.
4. После публикации выполнить readback `release.body` по тегу и сравнить с проверенным файлом. Несовпадение — ошибка публикации, требующая исправления.
5. Встроить этот gate как обязательный шаг *до запроса GitHub API на создание/обновление Release* во всех новых/редактируемых release-workflow; не привязывать к источнику сборки, ключу подписи или каналу доставки.

**Ограничение:** файлы политики/валидатора сами по себе не перехватывают произвольный вызов GitHub Releases API. Настоящая техническая блокировка наступает только в каждом workflow, использующем этот gate. Все новые публикующие workflow обязаны его подключать.

Проверка валидатором — структурная: автор обязан подтвердить реальность изменений по source diff и данным тестирования. Наличие русского текста не доказывает достоверность по существу.
